OpenFGA and SQL tables answer the same question in different places

Both store who has which role, and where. Neither stores a record per user per employee. The difference is where the rules live and who changes them.

OPENFGA

The model file holds what your role, permission and role_permission tables hold, plus the inheritance rule. This is the real fga/model.fga, one level shown.

type area
  relations
    define zone: [zone]                                    # parent link
    define admin: [user, ...] or admin from zone            # role, inherited from the zone
    define coordinator: [user, ...] or coordinator from zone
    define salary_coordinator: [user, ...] or salary_coordinator from zone
    define can_view_basic: admin or coordinator or salary_coordinator   # = role_permission
    define can_edit_basic: admin
    define can_view_salary: salary_coordinator

  user: 'user:deepak',
  relation: 'admin',
  object: 'area:delhi',

3. How "can Deepak edit employee e105?" is answered

SQL: MATCH THE COLUMNS

The employee row carries its zone, area and centre. The query compares them with Deepak's row.

ua.zone_id = e.zone_id
AND (ua.area_id   IS NULL OR ua.area_id   = e.area_id)
AND (ua.centre_id IS NULL OR ua.centre_id = e.centre_id)

5. The two real differences

WHO CHANGES THE RULES

SQL: "which role may do what" is data. An admin changes it instantly, with no review.

OpenFGA: it is part of the model. A developer changes it, tests it and deploys it.

WHAT HAPPENS WHEN THE TREE CHANGES

SQL: a grant row that says "Delhi, Rohini" matches nothing after Rohini moves to Punjab. Access is lost silently until someone fixes the row.

OpenFGA: the grant is on Rohini itself, so it follows Rohini.

6. Which to pick

SQL tables when it is one application on one database, with fixed levels and role-based access only. Lists and reports are one query, and there is nothing extra to run.
OpenFGA when many applications share the same zones, areas and centres, or when some need access to individual items, such as workflow approvals, health records or devices. The cost is one more service to run, a sync step from each application, and extra work for list screens.

7. Where "policy" fits

There are three ways to express who may do what. Real systems mix them. A policy is a rule written as code that looks at facts about the user, the record and the request, and answers allow or deny.

ROLES

Access comes from a job title.

"Admins can edit employees."

Your role and role_permission tables.

RELATIONSHIPS

Access comes from a link between a user and a thing.

"Deepak is admin of Delhi, and Rohini is in Delhi."

OpenFGA tuples, or your scope columns.

POLICIES

Access comes from a rule over attributes.

"Salary is visible only on the office network, and only for grades below 10."

Policy engines such as OPA and Cedar.

WHAT A POLICY LOOKS LIKE

An illustrative rule in the style of the Cedar policy language. It is not part of the POC.

permit (
  principal,
  action == Action::"viewSalary",
  resource
)
when {
  principal.role == "salary_coordinator" &&
  principal.zone == resource.zone &&
  resource.grade < 10 &&
  context.network == "office"
};

A policy engine holds the rules but usually no data. On every request the application must hand it the facts: the user's role and zone, the employee's zone and grade, the network. OpenFGA is the opposite: it holds the facts (tuples) and the rules are simple.

YOU ALREADY HAVE SMALL POLICIES

In OpenFGA: the department limit is a condition, which is a one-line policy attached to a grant.

condition in_department(allowed_departments: list<string>,
                        employee_department: string) {
  employee_department in allowed_departments
}

In SQL: the same policy is a line in the query: ua.department = e.department.

WHAT TO DO ABOUT IT

Now: no separate policy engine. Zones, areas, centres and roles are relationship data, and the few attribute rules fit in OpenFGA conditions or SQL.

Later: consider one if attribute rules multiply, for example approval limits by amount, access by shift or network, or configuration rules for switches and routers.
