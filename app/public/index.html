What OpenFGA stores

Everything the HR application itself stores. In this POC it is held in memory; in a real system it is the HR database. These are raw tables with no access control applied, so salary is visible to whoever opens this screen. Notice what is missing: there is no table of role grants here. Grants live only in OpenFGA.

employee HR application

One row per employee. unit and department are the two fields access depends on. The API sends department to OpenFGA with every check.

org_unit HR application

The organisation tree as the HR application knows it. Each row with a parent is also written to OpenFGA as one "tree link" tuple.

department HR application

Departments are plain values on the employee row. OpenFGA has no department objects.

user HR application

The demo logins. OpenFGA has no user table: a user exists there only when a tuple names them.

OpenFGA is the service that decides who may see what. It keeps only three kinds of thing.

Rules: general statements, such as "an Admin of a zone is also Admin of every area in it".

Facts: specific statements, such as "Anita is Admin of North Zone" or "Delhi belongs to North Zone". OpenFGA calls each fact a tuple.

A history of every fact added or removed.

It does not keep a list of who can see which employee. It works that out from the rules and facts each time it is asked.

In each table below, every entry is a sentence in plain English with its stored values on the line beneath. Everything is read live through OpenFGA's API. Behind the API these are the store, authorization_model, tuple and changelog tables in Postgres. No employee names, departments or salaries are here.

A list screen has to answer two questions at once: which employees match my filters, and which of those may I see?

    
The filters, sorting and paging are done by the HR database. The access rules are held by OpenFGA. Neither one can answer both questions alone, so the application has to combine them.
